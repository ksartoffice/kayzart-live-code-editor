# WordPress 5.9のスケジューラー互換性修正

実装・検証日: 2026-10-27（Asia/Tokyo）。ブランチ: `fix/action-scheduler-wp59`。
基点は`main`の`d2321a1`。無料テンプレートの機能変更は含まない。

## 変更と目的

WordPress 5.9の通常の管理画面で、同梱Action Scheduler（AS）4.0.0が未定義関数を呼び、HTTP 500で停止していた。Kayzartが宣言するWP 5.9以上という要件を維持し、AIジョブの登録・実行も成立する構成へ修正した。

- `Ai_Scheduler`で、WP 6.8未満には公式AS 3.6.4、6.8以上には現在のAS 4.0.0を選ぶ。通常の版選択が働くよう、`plugins_loaded`より前に片方だけの入口を読み込む。
- 3.6.4はComposerのinline packageとして別名管理し、公式コミット`e7dafe215be5ef823392204535ee2e241f99a8cb`へ固定した。4.0.0の依存は維持する。vendorの直接編集や、利用者のサイトでの追加ダウンロードは行わない。
- サイトで実際に選択されたASの版を確認し、4.0未満では異なるジョブまで同一扱いするunique登録を避ける。RESTの要求ID／新規作成判定、workerのclaim／state_versionによる重複実行防止は維持する。
- 完了・取り消し等の後始末では、そのジョブUUIDに一致する期限監視アクションをすべて解除する。再送由来の余分な監視が残ることを防ぎ、別ジョブは解除しない。

本体の変更箇所は`includes/ai/class-kayzart-ai-scheduler.php`、既存の`Ai_Worker`、プラグインの起動部分、Composer設定。新しいAPI画面・DBテーブル・外部配信サーバーは追加していない。

## 容量・コード量と保守負担

- 追加する旧版の配布対象は88ファイル、展開後477,246 bytes、単独圧縮の実測163,058 bytes（約160KB）。ライセンスも同梱する。
- 読み分けクラスは**51行・1,489 bytes**（コメント・空行を含む）。既存workerと起動処理の変更は数行で、増えるコードの中心はテストとCI。
- 両方の実行基盤を起動せず、既存のASの版選択で一つを使う。ジョブや定期処理を二重に実行する設計ではない。正確な起動時間やメモリ差のベンチマークは実施していない。
- AS 3.6.4は古い版であり、今後の修正・脆弱性情報の確認と保守は必要。監視対象はComposerの別名だけでなく、元の`woocommerce/action-scheduler`の3.6.4も含める。依存更新時には読み分けの境界・ライセンス・テストの再確認も行う。
- 他プラグイン同梱ASとの共有という既存仕様は維持する。今回確認したのは同梱3.6.4と4.0.0の前後登録であり、すべての第三者プラグインや非標準の起動順を保証するものではない。

## 回帰テスト

### PHP

- WP版による同梱パス、実際に選ばれたASの版・ソース・unique対応を確認するテストを追加。
- 異なる2ジョブの登録、両方の完了、次ジョブへの連鎖、期限監視の解除を検証するよう既存テストを強化。
- 初期アクションの重複・古いステップの再送で、完了したAI処理を再実行せず期限監視も残さないことを検証。
- 1ジョブを取り消しても、もう1ジョブの実行アクション・期限監視が残ることを検証。
- 通常のPHPUnit実行に加え、`KAYZART_TEST_AS_STORE=db`で本番のDBStoreを使う経路を追加。CIでも両経路を実行する。移行用ストアだけでは検出できなかった旧版uniqueの不整合を回帰対象にした。

### 実管理画面・配布ZIP

`tests/e2e/scheduler-compatibility.spec.ts`と専用CIを追加した。実際の配布ZIPを独立したWordPressへ展開して、次を確認する。

1. ログイン後のDashboard・Kayzart新規作成・設定がHTTP 200で、実際のフォームや管理画面が表示されること。
2. 別のASがKayzartの前／後に登録されても、対応する版・ソース・DBStoreが選ばれること。
3. 共通ヘルパーで作った固定ページをエディタで変更・保存し、再読込後も変更が残ること。finallyでページを削除し、成功を確認すること。
4. 以前のAS 4.0.0で作ったpendingアクションを、新しい構成で読み取り・実行でき、スキーマが巻き戻らないこと。準備用の明示的なCLI fixtureだけで旧構成のデータを作る。

fixtureは明示的な環境フラグがある使い捨てサイトだけで有効。外部HTTPとメールを遮断し、配布物には含めない。

## PR #143のP2指摘への追補（2026-10-27）

`unschedule_job()`には単件解除が残っており、AS 3.6.4の非unique登録で同じジョブの予約が重複すると、キャンセル後も期限監視（legacy実行モードでは実行予約も）が残ることを確認した。実行予約を`as_unschedule_all_actions()`へ変更し、期限監視は通常完了と共通の全件解除処理を使用する。

stepwise・legacyの両モードで実行予約と期限監視を各3件用意する回帰テストを追加した。キャンセル直後、workerを追加実行せずに全件がcanceledとなり、別ジョブ・別グループの予約がpendingのままであることを検証する。旧版が作った重複キューを、新しいASで処理するケースも同じfixtureで検証する。

- 修正前: WP 5.9のDBStoreで2件とも失敗し、pendingの残存を再現。
- 修正後: DBStoreのAI・REST関連はWP 5.9／PHP 7.4で61件・320 assertions、WP 7.1.3／PHP 8.2で61件・318 assertions合格。
- 変更したworkerのPHPCS・PHP互換性、`git diff --check`合格。
- 通常のテスト用ストアでも、両環境で追加2件・66 assertions合格。

## 再現・残作業

PHPUnitは通常実行と、次のDBStore経路を使う。ローカルで実行する場合は、既存の利用者DBではなく独立したWPテスト設定を必ず指定する。

```sh
KAYZART_TEST_AS_STORE=db vendor/bin/phpunit --filter 'Test_Kayzart_Ai_Scheduler|Test_Kayzart_Ai_Worker|Test_Kayzart_Ai_Immediate_Dispatcher|Test_Kayzart_Rest_Ai'
```

ブラウザの独立サイト構築・配布物展開・既存アクション準備は`.github/workflows/scheduler-compatibility.yml`を基準とする。ローカル検証環境は`C:/Users/Inagaki/AppData/Local/Temp/kayzart-wp59-research-20261027/implementation/`で、各版の結果・サーバーログを保存している。

確認後、一時ページは回収済み。今回起動した4本のPHPサーバーを停止し、検証用MariaDBも正常終了した。

残る手順はPRレビュー、リモートCI、リリース番号と配布の決定。テンプレート機能ブランチへは、この修正を取り込んだ後にテンプレート自体のWP 5.9 E2Eを実行する。mainへのマージ・本番配布はこの作業では行っていない。
