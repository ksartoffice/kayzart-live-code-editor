# WordPress 5.9とAction Schedulerの互換性調査

調査日: 2026-10-27（Asia/Tokyo）。ブランチ: `fix/action-scheduler-wp59`。
基点: `main`の`d2321a1`（3.4.3）。テンプレート機能ブランチの実装は取り込んでいない。

## 結論

**WP 5.9対応を維持し、AI実行基盤を動かす構成は実現可能。隔離コピーで試作と動作確認まで実施した。**

第一候補は、新しいWPでは現在のAction Scheduler（AS）4.0.0を維持し、古いWP向けには公式3.6.4のソースを別枠で同梱して、読み込む方を切り替える構成。そのうえで、ASの版によるジョブ登録の意味の違いをKayzart側で吸収する。

**本ブランチのランタイム・composer.json・composer.lock・vendorは変更していない。** 変更したのは調査用コピーだけで、本実装・回帰テストのリポジトリへの組み込みはこれから。ブランチ上にはこの調査記録を保存する。

## 問題の確認

- KayzartはWP 5.9以上を宣言するが、AS 4.0.0の要件はWP 6.8以上。
- AS 4.0.0の管理画面初期化が`wp_is_serving_rest_request()`を呼ぶ。これはWP 6.5導入のため、WP 5.9では未定義関数のfatalになる。
- `main`にも同じ依存指定がある。テンプレート追加によって発生したものではない。
- 通常のPHPUnitでは`is_admin()`が偽になり、この呼び出しが通らない。古いWPのブラウザによる管理画面確認が必要。

根拠: [AS 4.0.0の変更と要件](https://developer.woocommerce.com/2026/06/17/changes-to-action-scheduler/)、[WordPress関数の導入版](https://developer.wordpress.org/reference/functions/wp_is_serving_rest_request/)。

## 旧版への単純な差し替えでは不十分だった

3.6.4は、3.7からのL-2対応方針変更より前の候補。WP 5.9／PHP 7.4で起動し、Kayzartが使うAPIや優先度指定も利用できた。ただし、`$unique=true`の意味に重要な違いがある。

| 版 | 通常のDBStoreでの重複判定 |
|---|---|
| 3.6.4 | 同じhookとgroupの待機中／実行中アクションを重複扱いする |
| 4.0.0 | hook・groupに加え、引数も一致するものを重複扱いする |

Kayzartは、異なるジョブにも同じhook・groupを使い、UUIDなどを引数に入れる。旧版で既存コードのまま登録すると、**別のジョブまで重複扱いされ、登録されない**。

通常のDBStoreに、異なる引数で2件登録する実験では、最初のIDは取得できたが2件目は`0`だった。既存の`test_completion_dispatches_next_pending_job`も、DBStoreを明示的に選ぶと失敗した。

一方、最初に全体テストを実行したときは失敗しなかった。確認すると、選択されていたのは移行用の`ActionScheduler_HybridStore`で、同じ条件を検証できていなかった。**管理画面だけでなく、テスト時の実ストアも確認すべき**という追加の調査結果である。

根拠: [4.0.0の重複判定変更](https://developer.woocommerce.com/2026/06/17/changes-to-action-scheduler/)、[3.7からの要件変更](https://developer.woocommerce.com/2023/10/24/action-scheduler-to-adopt-l-2-dependency-version-policy/)。

## 成立を確認した試作構成

| 項目 | 試作での扱い |
|---|---|
| WP 5.9〜6.7向けの読み込み分岐 | 公式AS 3.6.4を選択。実機確認済みなのは5.9 |
| WP 6.8以上向けの読み込み分岐 | 現行AS 4.0.0を選択。今回のテストは7.1.3 |
| 配布方法 | 両方をComposer管理し、起動時に片方だけを読み込む |
| 古いASでの初期ジョブ・期限監視の登録 | hook＋groupだけのunique抑止を使わない試作。REST側の要求ID、新規作成判定、workerのclaim／state_versionによる制御と合わせる |
| 継続ステップ | 現行の`$unique=false`による登録を維持 |
| 定期的な掃除・回復処理 | 引数で別ジョブを区別するものではないため、既存のunique登録を維持 |

Composerでは通常、同じパッケージの2バージョンをそのまま同時指定できない。そのため、試作では4.0.0を正規名`woocommerce/action-scheduler`で管理し、3.6.4をinline package定義のローカル別名`kayzart/action-scheduler-legacy`で管理した。**公開Packagistパッケージを新設したわけではない。**

旧版は公式ソースのコミット`e7dafe215be5ef823392204535ee2e241f99a8cb`を固定し、元のGPLライセンスを保持する。この構成でComposerによる取得・共存が可能なことを確認した。配布後にユーザー環境から旧版をダウンロードさせる仕組みは不要。

試作のunique調整は成立確認のための最小変更であり、そのまま本番仕様として確定しない。同一要求の再送、同一ジョブの重複アクション、キャンセル、期限監視の後始末を含む正式なテストで、Kayzart側の制御との整合を確認する。

## 実測結果

| 検証 | 結果 |
|---|---|
| 旧版単体・既定の移行用ストア、WP 5.9／PHP 7.4 | 全668件中16 skip、失敗なし。ただしDBStoreの問題を見逃した |
| 旧版・DBStore指定、unique調整前 | AI worker／即時実行の24件中1件失敗。次の別ジョブへの連鎖実行が成立しない |
| 版別依存＋unique調整、DBStore指定、WP 5.9／PHP 7.4 | 668件中652件合格・16 skip、2,880 assertions、失敗なし |
| 同じ試作、DBStore指定、WP 7.1.3／PHP 8.2 | 668件合格、2,983 assertions |
| ブラウザ・WP 5.9／PHP 7.4、元のAS 4.0.0 | 認証後の`/wp-admin/`でHTTP 500を再現 |
| 同じブラウザ・試作の版別依存 | `/wp-admin/`、Kayzart新規作成、Kayzart設定の3画面がHTTP 200で表示 |
| 既存データの読み取り | AS 4.0.0が作ったpendingアクションを3.6.4で読めた。ID・引数・pending状態が保持された |
| スキーマ | 上記の切り替え後もStoreSchemaは8のまま。旧版によるスキーマの巻き戻りは起きなかった |
| Composer本番依存の監査 | 試作の`composer audit --locked --no-dev`で指摘なし。将来の保守や全脆弱性への保証を意味しない |

5.9のskipは、履歴など新しいWP機能を前提とした既存テストによるもの。AIは既存のfake clientを使い、課金される実API呼び出しは行っていない。キュー・claim・worker・結果保存・キャンセル・期限監視等は既存のAIテストを実行した。

管理画面の確認は、同じ隔離コピーの依存選択を一時的に元のASへ戻すと500、試作へ戻すと200になることも確認した。このため、単に正常な別環境を見ただけでなく、追加するブラウザ回帰テストが元の不具合を検出できることを確認できた。

## 本実装に追加する回帰テスト

1. **実際の古いWP管理画面を開くブラウザテスト**
   - WP 5.9／PHP 7.4の独立サイトへ、実際の配布依存を含めてプラグインを導入する。
   - ログイン後、Dashboard・Kayzart新規作成・設定を開く。
   - HTTP 200だけでなく、認証済みの管理画面・該当フォームが描画されることも確認する。ログイン画面への戻りや200のエラーページを合格扱いにしない。
   - 新規データは`page`、共通ヘルパー、finallyによる削除と成功確認を使う。
2. **DBStoreを使うAI基盤の回帰**
   - 異なる2ジョブを同時に待機させ、両方の実行・完了と次ジョブへの継続を確認する。
   - 同じ要求の再送でAI処理が重複しないこと、ステップの再送、キャンセル・期限切れ・再回復・後片付けを確認する。
   - 外部AIはfake clientで代替し、ネットワークと課金を伴わせない。
   - 移行用ストアも従来どおり検証し、通常DBStoreだけに偏らせない。
3. **版の境界と既存データ**
   - 最低5.9、新しいWP、旧版を選ぶ上限6.7／新しい版を選ぶ下限6.8で実施する。
   - 使用中のASの版・読み込み元・ストアをテスト内で確認する。
   - 元のAS 4.0.0が作ったテーブル・待機ジョブからの移行、他プラグイン同梱ASとの読み込み順を検証する。

CIは、既存PHPUnitマトリクスに加え、独立したWordPressサイトとブラウザを起動するジョブを追加する方針で実現できる。管理画面を模した単体テストだけで代用しない。

## 選択肢と残る判断

| 案 | 評価 |
|---|---|
| **新旧の版別同梱＋Kayzart互換層** | 第一候補。今回、動作する試作を確認できた。旧版の保守と配布構成は明示的に管理する必要がある |
| 全環境を3.6.4へ戻す | 新しいWPまで古いライブラリへ戻すため推奨しない |
| AS 4.0.0のWP 5.9向け互換forkを保守 | 技術的な候補。ただし公式の最低要件外を自分たちで保守することになる。今回試作していない |
| 古いWPだけ別のWP-Cron実行基盤へ置換 | ASストア・claim・即時実行に依存する既存コードの変更が広がる。今回の修正としては大きい |
| 未定義のWordPress関数だけ補う | 公称要件の不整合や別の互換差の確認が残る。今回の目標を満たしたとは扱わない |

ASは、同じサイト上で登録された複数の版のうち新しいものを選ぶ仕組みを持つ。版別同梱は、異なるASを同時に独立実行する仕組みではない。他プラグインが登録したASの選択も考慮し、実装では実際に選ばれた版に対して互換層を適用する。[公式の読み込み・版選択の説明](https://actionscheduler.org/usage/)

3.6.4は古いリリースであり、公式が現在もWP 5.9向けに更新を続けているわけではない。将来の修正確認・保守を引き受ける前提が必要。本調査で全WP／PHP版、すべての他プラグイン、全ジョブ形式の移行、並列負荷試験まで完了したとは扱わない。
