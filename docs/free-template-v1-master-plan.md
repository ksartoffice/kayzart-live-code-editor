# 無料テンプレート第1弾 マスタープラン

- 作成日: 2026-10-26（Asia/Tokyo）
- 対象: `kayzart-live-code-editor` 無料版
- 作業ブランチ: `feat/bundled-free-template-v1`
- 基点: ローカル `main` の `d2321a1`（作成時のプラグイン版は3.4.3）
- 状態: **計画レビュー用。機能・テンプレート・画像は未実装。**
- リリース番号・公開日: 未定

## 1. このリリースで達成すること

**プラグインに同梱した汎用LPテンプレート1点を選び、AI設定やテンプレート配信サーバーへの接続なしで、新規ページの編集・公開まで進められるようにする。**

「完成見本を選ぶ → 下書きを作る → 文章・画像・リンクを差し替える → プレビュー → 公開」を第1弾の完結した体験とする。

テンプレートから作成したページは、その時点のHTML・CSS・画像参照を保持する独立したコピーにする。以後のテンプレート更新・提供終了で作成済みページを書き換えない。ページ表示・編集に必要なKayzart自体の無効化後まで動作を保証する計画ではない。

この文書を今回の計画の基準とし、過去の「Pro加入で全テンプレートを提供」「外部カタログを常時取得」といった案を、そのまま今回の要件として扱わない。

## 2. 合意した方針と、レビュー対象の設計案

### 2.1 合意した方針

| 項目 | 方針 |
|---|---|
| 段階的な公開 | まず無料テンプレート第1弾を作る。有料販売・アップロード・既存ページへの適用は後続に分ける |
| 収録数 | 業種共通の汎用LPを1点 |
| 画像 | サムネイルは写真入りの完成イメージ。作成されるページの画像部分はプレースホルダー |
| プレビュー | 詳細では、実際に適用されるプレースホルダー版を確認できる |
| 写真の説明 | 選択前に、写真は使用例でありページ作成時には含まれないことを伝える |
| 配布 | 一覧情報・テンプレート・サムネイル・プレースホルダーをプラグインに同梱 |
| 通信 | テンプレート機能のための外部通信・会員登録・購入認証は不要 |
| 保存 | 作成済みのHTML・CSSをDBへ保存。プラグイン内の元ファイルへ編集結果を書き戻さない |
| 将来 | 有料テンプレートを買い切り販売し、購入ZIPをアップロードして使える方式を別途実装する |

### 2.2 本計画で提案する初期仕様

以下は合意した目的を具体化する設計案であり、特に第14章の項目をレビューで確認する。

- Add newを入口とし、「テンプレートから／AIで作成／白紙から」の3つの開始方法を提示する。
- テンプレート経由は第1弾では固定ページ（`page`）の下書き作成に限定する。既存のAI・白紙経由の投稿タイプ対応は維持する。
- 汎用LPは日本語を初期言語とし、Tailwindモード＋独立ページ表示（Standalone）を明示設定する。
- 商品・サービス紹介と問い合わせ導線を基本用途とする。配色、書体、写真の点数、具体的な文面は制作タスクで確定する。
- プレースホルダーは同梱PNGを基本案とし、必要ならWebPを評価する。メディア登録のためにSVG許可を追加しない。
- ページで使用するプレースホルダーは、ページ作成時にローカルファイルからメディアへコピーする。
- 初回表示は既存のAI・白紙フローを保ち、テンプレート経由へ進んだときだけ一覧を表示する案を基本とする。最終配置はP0で決める。

## 3. 第1弾の範囲

### 含めるもの

1. 完成した汎用LP1点、写真入りサムネイル、プレースホルダー、素材ライセンス記録。

6. メディア登録、画像参照置換、重複送信・失敗時の処理。
7. 作成直後の差し替え案内、必要な翻訳・ドキュメント・テスト・配布確認。

- 有料マーク、価格・購入リンク、Lemon Squeezyとの連携。
- ZIPアップロード、追加済み管理、自作テンプレート保存・書き出し。
- 独立したテンプレート管理メニュー、検索・カテゴリ絞り込み。

将来との接続点はID・バージョン・コンテンツ・画像参照の形式までにとどめる。第1弾で有料機能の無効化コードやZIP処理を先行実装しない。

## 5. 作成物と配置案

下記は新規ファイルの配置案。既存のPHP描画用`templates/`と区別する。

```text
assets/templates/
  catalog.json
  free/general-service-lp.json
  thumbnails/general-service-lp.webp
  placeholders/landscape.png
  licenses/README.txt

includes/
  class-kayzart-template-library.php
  class-kayzart-template-page-creator.php

scripts/templates/
  build-template-assets.mjs
  （必要な撮影用ソース・ローカル写真・ライセンス記録）

docs/
  free-template-v1-master-plan.md
```

- `assets/templates/`の定義・画像・ライセンス記録は配布ZIPに含める。利用者入力によるファイル追加は第1弾では行わない。
- 写真入りの見本は開発時の撮影用にだけ使用する。元写真をページ作成用データへ入れない。
- サムネイル自体は配布物であるため、その中に写る写真にも配布に適した権利・GPL互換性を確認する。「元写真を同梱しない」だけで確認を省かない。
- 定義は人が編集できるJSONを正本とし、画像とプレビュー生成を検証ツールで扱う。定義の別コピーを複数フォルダで手管理しない。
- `docs/`と`scripts/`は現行`.distignore`で配布対象外。実行時にこれらを参照しない。
- `assets/dist/`はビルド生成物として扱い、手編集・Git追加しない。

## 6. 汎用LPと画像の制作仕様

### 6.1 ページ構成案

| 部分 | 制作内容 |
|---|---|
| ヘッダー | 文字でも成立する事業名、ページ内ナビ、問い合わせ先への導線 |
| メインビジュアル | 見出し、説明文、行動ボタン、差し替え画像 |
| 特徴 | 選ばれる理由を3点程度 |
| サービス内容 | 業種固有の機能に依存しない紹介カード |
| 料金 | 料金・提供内容の差し替え例。サンプル価格と分かる案内 |
| 利用の流れ | 相談から利用開始まで |
| FAQ | サービスに合わせて変更できる質問・回答 |
| 問い合わせ・フッター | 設定箇所が明確な連絡先、事業者情報 |

完成ページの縦構成を用意する。実績数値、口コミ、受賞歴、所在地などの事実を創作して実在情報のように置かない。ダミー情報は架空のサンプルだと分かるものにする。

フォーム送信バックエンドは実装しない。未設定の問い合わせボタンは押しても動かないよう放置せず、初期状態ではページ内の「連絡先を設定する説明」へ移動する。全アンカー先を用意し、利用者が既存フォーム・予約ページ・連絡先へ差し替えられるようにする。

テンプレート内のJavaScript、イベント属性、外部スクリプト、カスタムheadは第1弾では不要な構成にする。FAQはHTMLで表示できる構成とし、`unfiltered_html`のない利用者でも保存後に崩れない要素だけを採用する。

### 6.2 画像・フォント

- サムネイルは、実テンプレートのプレースホルダー画像だけを撮影用写真へ置換して撮る。HTML・CSSのレイアウトを別物に作り替えない。
- 一覧から選ぶ前と詳細の両方で、写真が使用例であることを短く伝える。文言例:「写真は使用例です。作成後にご自身の画像を設定してください。」翻訳対象にする。
- 詳細プレビューはプレースホルダー版を表示し、作成後の状態を事前確認できるようにする。
- 写真とプレースホルダーの表示比率・枠寸法をそろえる。1枚を複数箇所で使う場合も、既存の画像差し替え操作で各箇所を独立して変更できることを確認する。
- ページ内画像は通常の`img`を基本とし、CSS背景画像や複雑な`picture`による差し替え難度を増やさない。
- 表示はシステムフォントを基本とする。閲覧時にGoogle Fontsなどを要求しない。
- 写真・プレースホルダー・アイコンのライセンス、出典、加工内容を記録する。自作・権利確認済みの素材を選ぶ。
- 画像サイズ・配布容量はP1で計測する。現時点で根拠のない容量値をリリース要件として固定しない。

## 7. 一覧・定義データの形式案

第2弾のZIPでも同じページ定義を運べるようにするが、ZIPの仕様・購入認証・権利管理はここでは実装しない。

| データ | 最低限持つもの |
|---|---|
| カタログ | `schemaVersion`、テンプレートID、名前、説明、言語、版、ローカル定義パス、ローカルサムネイルパス |
| ページ定義 | `schemaVersion`、`id`、`version`、`kind: page`、`locale`、`cssMode`、`layoutMode`、HTML・CSS、画像宣言 |
| 画像宣言 | 定義内の画像ID、相対ファイルパス、形式・寸法、代替テキスト |

例（配布定義の形を説明する抜粋。省略された本文を完成テンプレートとして扱わない）:

```json
{
  "schemaVersion": 1,
  "id": "general-service-lp",
  "version": "1.0.0",
  "kind": "page",
  "locale": "ja",
  "cssMode": "tailwind",
  "layoutMode": "standalone",
  "content": {
    "html": "<section><img src=\"{{asset:main-visual}}\" alt=\"画像を差し替えてください\" width=\"1600\" height=\"900\"></section>",
    "css": "@import \"tailwindcss\";\n"
  },
  "assets": [
    {
      "id": "main-visual",
      "path": "placeholders/landscape.png",
      "mimeType": "image/png",
      "width": 1600,
      "height": 900
    }
  ]
}
```

- `{{asset:...}}`はテンプレートに宣言された既知IDだけを解決する。プレビューでは同梱画像URL、作成時には登録したメディアURLへ置換する。
- 未解決参照、ID重複、未知のschema、未対応モード、外部ファイルパスはエラーにする。
- 定義の相対パスは固定のテンプレートディレクトリ配下に限定する。ブラウザから任意のパス・URL・HTML・CSSを受け取って作成しない。
- 版は「データ形式の版」と「各テンプレートの版」を分ける。同じIDの改版は次の新規作成にだけ反映する。
- 表示名・説明の翻訳方法はP0で確定する。管理画面の翻訳と、ページ本文の言語を混同しない。

## 8. Add newとプレビューの動作

1. Add newで開始方法を選ぶ。AI用の接続案内はAI経由の文脈で表示し、テンプレート経由では接続設定を要求しない。
2. テンプレートカードに写真入りのサムネイル・名前・用途・写真の説明を表示する。
3. 詳細を開くとプレースホルダー版を表示する。PC・スマホ幅を切り替えられる。
4. タイトルを入力して「このテンプレートで作成」を押す。空欄なら翻訳可能な仮タイトルを使用する。
5. 成功時は内容入りの下書きのKayzartエディタを開く。画像・文章・連絡先を変更する短い案内を表示する。

テンプレート選択から戻っても入力したタイトルやAI指示を不用意に消さない。AI指示がフォームに残っていても、`start_mode=template`ではAIへ送信せず、初回AIリクエストも保存しない。

テンプレート経由のCSSモード・表示モードは定義に従う。Normal/Tailwindの選択を誤って適用して壊さないよう、当該経路ではモードを説明表示にする。AI・白紙経由の選択肢は維持する。

プレビューは投稿IDを必要としない読み取り専用の表示とし、初期案ではAdd new用の同梱データとPHPコンパイル結果を使う。既存の投稿用`/compile-tailwind`をダミー投稿付きで呼ばない。実際の保存と同じ候補抽出・コンパイル処理を利用する。

プレビューは隔離されたiframeなどに表示し、ページ内のスタイルを管理画面へ漏らさない。スクリプト・フォーム送信・外部リソース・上位画面への遷移を許可しない。PC・スマホ切替、閉じる操作、フォーカス復帰、キーボード操作を確認する。

## 9. ページ作成と保存の実装方針

### 9.1 作成処理の流れ

1. nonce、ログイン、`page`の作成権限、Kayzartでの固定ページ有効状態、画像登録に必要な`upload_files`を検証する。
2. テンプレートID・リクエストID・タイトルを受け取り、サーバー内のカタログから定義を解決する。
3. 定義・同梱画像を検証し、HTMLの許可要素処理、Tailwind候補抽出・コンパイルを行う。コンパイルなど事前に検証できる処理は下書き作成前に行う。
4. 同梱プレースホルダーをサイトのメディアへ登録するか、有効な既存登録を再利用する。ローカルコピーを使い、HTTPで自サイトへ取りに行かない。
5. 画像参照をメディアURLへ置換し、通常の固定ページの下書きとして本文・CSS・モードなどを保存する。
6. 保存内容を確認してから、既存のエディタURLへ遷移する。

作成処理は既存のnonce付きadmin actionを拡張する案を基本とする。新しい公開REST APIや、外部配信サーバーは必須にしない。

### 9.2 保存でそろえるもの

- `post_type=page`、`post_status=draft`、作成者、タイトル、本文。
- Kayzart有効化、セットアップ完了、Tailwindモードとモード別CSS、生成CSS、候補クラス。
- `_kayzart_template_mode=standalone`を明示し、サイト既定のThemeモードに引っ張られないようにする。
- 使用したテンプレートID・版と、ページが参照するメディア。
- 初期スナップショット・履歴との整合。最低WordPress版ではフル履歴対応を前提にしない。

`_kayzart_css`だけを書いて終わりにしない。保存形式は現在の`Rest_Save`、`Css_Mode`、`Snapshot`と整合させる。共通化が必要なら小さな内部処理を抽出し、既存のAI・白紙・通常保存の挙動を変えない範囲にする。

### 9.3 画像の寿命と権限

- サムネイルと詳細プレビューは同梱パスを参照してよい。作成したページの画像はuploads内のメディアURLを参照する。
- メディア再利用はテンプレート／画像の識別情報と内容ハッシュなどで判定し、添付情報・実ファイルの存在も確認する。新規作成ごとに同じ画像を不要に増やさない。
- 再利用画像は利用者が差し替えても他ページの元画像を変更しない。メディア自体を利用者が削除した場合まで自動修復を保証しない。
- `upload_files`を持たない利用者へ権限を自動付与しない。テンプレート経由では理由を案内し、AI・白紙経由の既存権限は維持する。この制約の妥当性をレビューする。
- サムネイル撮影用の元写真は、利用者のメディアへ登録しない。

### 9.4 重複送信と失敗

- 送信中はボタンを無効化する。加えてユーザーと作成リクエストIDをひも付け、同じ要求の再送で新しい下書きを増やさない。
- 同一要求の並行実行は原子的に予約し、処理中の要求を重ねて実行しない。サーバー側の予約・結果保持にはWordPress標準の保存機構を使い、新しい専用テーブルは基本案に含めない。
- 予約の期限・完了した投稿ID・失敗状態を扱い、ブラウザへの応答だけが失われた場合は作成済み下書きへ復帰できるようにする。保存方式と保持期間はP3着手時に具体化する。
- 定義不正・コンパイル失敗・画像登録失敗を成功扱いにしない。入力とエラーを保ち、再試行できる表示にする。
- 作成途中で失敗した場合は、その要求が新規作成した未完成下書きだけを回収する。既存投稿・再利用した共有メディアを削除しない。
- 回収に失敗した場合も成功遷移せず、管理者が確認できる情報を残す。DBトランザクションだけで投稿・ファイルを一括回収できると仮定しない。

## 10. セキュリティ・互換性・掲載ルール

- PHP 7.4以上、現行のWordPress最低要件5.9を維持する。PHP 8限定構文を使わない。
- 固定ページ作成・メディア登録の権限とnonceをサーバーで確認する。管理画面が見えるだけで作成を許可しない。
- 同梱HTMLも現行の保存ポリシーに沿って扱う。`unfiltered_html`のない利用者を、任意コード挿入経路で迂回させない。
- パスはカタログ内の許可済みファイルから決める。パストラバーサル・任意URL指定・未知のテンプレートIDを拒否する。
- HTML・CSS・画像URL・翻訳文字列は、それぞれの出力先で適切に扱う。テンプレートのスタイルやタグを管理画面へ直接流し込まない。
- テンプレート機能による外部HTTP、外部画像、外部フォント、分析タグ、バックグラウンド同期を追加しない。既存のWordPress更新通信などまで停止する意味ではない。
- 同梱JSON・写真入りサムネイル・プレースホルダーを含め、配布ファイルのGPL互換性・出典を確認する。素材を後から揃える場合は、権利確認をP1の完了条件に含める。
- 第1弾に購入解除を前提とするテンプレート本体・機能を含めない。今回の設計を理由に将来の有料版の掲載適合まで保証しない。

参照した公式資料（確認日: 2026-10-26）:

- [WordPress.org Detailed Plugin Guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/) — 同梱物のライセンス、第5条の機能制限、第7〜8条の外部通信・コード配信。
- [WordPressの画像MIME一覧](https://developer.wordpress.org/reference/functions/wp_get_mime_types/) — PNG/WebPなど。実際の許可形式・画像処理可否はサイト環境でも確認する。

## 11. 実装順序と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| P0: 計画・仕様レビュー | 本計画のレビュー、未決事項の確定、データ形式と画面ラフ | 第14章の実装を止める項目が解決し、仕様と受入条件が一致している |
| P1: テンプレート制作 | 汎用LP・プレースホルダー・撮影用写真・サムネイル・素材記録 | 完成ページになっており、写真説明と実適用版を確認でき、配布素材の権利が明確 |
| P2: ローカル基盤 | カタログ・定義検証・ローカルプレビュー・コンパイラ連携 | 外部通信やDBへの投稿作成なしで正しく読み込み・表示できる |
| P3: 新規作成 | 画像登録・下書き作成・モード保存・重複／失敗処理 | 正しい下書きだけを作成し、二重送信・異常時に不要な投稿や画像を残さない |
| P4: Add new・編集案内 | 開始方法選択・詳細・PC/スマホ・作成・差し替え案内・翻訳 | テンプレート経由が完結し、AI・白紙の既存導線も使える |
| P5: 配布・リリース確認 | テスト、ライセンス、readme、ビルド、配布ZIP確認 | 第12章を満たし、PRレビューとリリース準備が完了 |

P1〜P4は必要に応じて縦に小さく実装し、動く1経路で結合する。途中コミットでレビュー可能にし、未完成の開始方法をmainや公開版へ出さない。P0の外部AIレビューは本計画と現行ソースに対するレビューであり、実装・素材制作・公開の依頼ではない。

作業は今回のブランチから開始する。実装時にPRを分割する場合も、独立して機能する変更だけをmainへ取り込む。第1弾の公開は下記の受入条件がそろってから行う。リリース番号・タグ・SVN配布の時点は別途決める。

## 12. テストとリリース受入条件

### 12.1 必須の受入条件

- [ ] 同梱テンプレートは業種共通の完成LP1点で、旧3サンプルを完成品として混在させない。
- [ ] サムネイルでは写真入りの完成イメージを示し、写真が含まれない説明を選択前に読める。
- [ ] 詳細プレビューはプレースホルダー版で、閲覧・幅変更・閉じる操作では投稿・添付ファイルが増えない。
- [ ] AI未設定でもテンプレートから新規作成でき、AIリクエストは実行・予約されない。
- [ ] テンプレート関連の外部通信がなくても、一覧・プレビュー・作成・公開表示が成立する。
- [ ] 新規データは`page`の下書きで作成され、本文・CSS・Standalone・モード別CSS・画像参照が保存される。
- [ ] 初回表示、再編集、保存、公開後もTailwindのデザインが一致する。
- [ ] 保存済みページからプラグイン内のページ用画像を直接参照せず、未解決の画像トークンが残らない。
- [ ] 画像・文章・リンクを既存の要素編集機能で差し替えられる。
- [ ] PC・スマホで表示が成立し、全アンカー先が存在し、未設定の問い合わせ先が明確である。
- [ ] 管理者・通常の編集者・作成権限なし・画像登録権限なしの挙動が仕様に一致する。
- [ ] 二重クリック・同一要求の再送・並行要求で、同じ下書きが複数できない。
- [ ] 定義破損・未知ID・nonce不正・コンパイル／画像登録／保存の失敗を成功扱いにせず、回収対象を誤らない。
- [ ] 作成済みページを編集した後にテンプレート定義・版が更新されても、編集結果を上書きしない。
- [ ] AI・白紙経由、既存投稿の編集、通常保存・モード切替が回帰しない。
- [ ] 現行最低要件と最新の対応検証環境で動作する。履歴非対応環境を除外せず確認する。
- [ ] 配布ZIPに必要な定義・画像・ライセンスがあり、開発用写真・撮影ソース・不要ファイルが混入しない。

### 12.2 自動テストの重点

- PHP: カタログ／定義検証、許可パス、権限、正しい保存状態、画像再利用、再送・競合、失敗時の回収を中心にテストする。
- フロント: 開始方法の切替、AI指示が残る場合の誤送信防止、写真説明、入力保持、送信中制御を確認する。
- E2E: AI未設定での一覧→詳細→下書き→画像差し替え→保存→公開表示の1経路を優先する。外部通信を遮断して、テンプレート経路が依存していないことを検証する。
- E2Eの新規データは必ず固定ページ。共通ヘルパーにテンプレートUIで作成された投稿IDの捕捉・回収を組み込み、作成・変換・削除を共通化する。
- 一時ページは`finally`で削除し、削除レスポンス成功を検証する。再ログイン・画面遷移後は現在のREST nonceを取り直す。`wp-json/wp/v2/kayzart`を呼ばない。
- テスト用添付ファイルも識別・回収し、既存の利用者データや共有添付を削除しない。

### 12.3 検証コマンドと配布手順

実装した範囲に合わせて既存の`npm run test:unit`、`composer test`、`composer phpcs`、`npm run e2e -- <対象spec>`を使う。PHP互換性チェック・Plugin Check・実配布ZIP確認もリリース前に実施する。前提環境不足のチェックを「合格」と記録しない。

ビルド前に、絶対パスがこのリポジトリ内の`assets/dist/`であることを検証して古い成果物をクリーンし、`npm run build`で再生成する。生成物を手編集・Git追加しない。`scripts/plugin-zip.mjs`は作業ツリーを`.distignore`で選別するため、同梱資産と撮影用ファイルの両方について実際のZIP内容を検査する。

readme・変更履歴・必要な管理画面翻訳を更新する。素材ライセンス記録と写真説明の翻訳も配布物で確認する。mainへの取り込みはPR経由とし、実装完了と本番リリースを別の状態で記録する。

## 13. 後続への接続点

- 第2弾は、同じページ定義・画像宣言を持つ有料パックのZIP取り込みと、商品紹介・購入導線を追加する。
- カタログが増えた段階で絞り込み・専用管理画面を追加する。第1弾で空の有料タブを作らない。
- 第3弾の既存ページ置換は、未保存内容の退避・保存前の取り消し・保存後の復元を別途設計する。
- 共有セクションやテンプレートとのライブ同期は、コピーして使う第1弾の仕様に持ち込まない。
