## 1. このリリースで達成すること

**プラグインに同梱した汎用LPテンプレート1点を選び、AI設定やテンプレート配信サーバーへの接続なしで、新規ページの編集・公開まで進められるようにする。**

「完成見本を選ぶ → 下書きを作る → 文章・画像・リンクを差し替える → プレビュー → 公開」を第1弾の完結した体験とする。

テンプレートから作成したページは、その時点のHTML・CSS・画像参照を保持する独立したコピーにする。以後のテンプレート更新・提供終了で作成済みページを書き換えない。ページ表示・編集に必要なKayzart自体の無効化後まで動作を保証する計画ではない。

この文書を今回の計画の基準とし、過去の「Pro加入で全テンプレートを提供」「外部カタログを常時取得」といった案を、そのまま今回の要件として扱わない。

## 2. 合意した方針と、レビュー対象の設計案

### 2.1 合意した方針

| 項目 | 方針 |
|---|---|
| 段階的な公開 | まず無料テンプレート第1弾を作る。有料販売・アップロード・既存ページへの適用は後続に分ける |
| 収録数 | 業種共通の汎用LPを1点 |
| 画像 | サムネイルは写真入りの完成イメージ。作成されるページの画像部分はプレースホルダー |
| プレビュー | 詳細では、実際に適用されるプレースホルダー版を確認できる |
| 写真の説明 | 選択前に、写真は使用例でありページ作成時には含まれないことを伝える |
| 配布 | 一覧情報・テンプレート・サムネイル・プレースホルダーをプラグインに同梱 |
| 通信 | テンプレート機能のための外部通信・会員登録・購入認証は不要 |
| 保存 | 作成済みのHTML・CSSをDBへ保存。プラグイン内の元ファイルへ編集結果を書き戻さない |
| 将来 | 有料テンプレートを買い切り販売し、購入ZIPをアップロードして使える方式を別途実装する |

### 2.2 本計画で提案する初期仕様

以下は合意した目的を具体化する設計案であり、特に第14章の項目をレビューで確認する。

- Add newの上部に「テンプレートから／AIで作成／白紙から」の3つの開始方法を常に提示する。開始方法の選択はAI接続案内より先に置く。
- テンプレート経由は第1弾では固定ページ（`page`）の下書き作成に限定する。既存のAI・白紙経由の投稿タイプ対応は維持する。
- 汎用LPは日本語を初期言語とし、Tailwindモード＋独立ページ表示（Standalone）を明示設定する。
- 商品・サービス紹介と問い合わせ導線を基本用途とする。配色、書体、写真の点数、具体的な文面は制作タスクで確定する。
- プレースホルダーは同梱PNGを基本案とし、必要ならWebPを評価する。メディア登録のためにSVG許可を追加しない。
- ページで使用するプレースホルダーは、ページ作成時にローカルファイルからメディアへコピーする。
- AIが利用できない初期状態ではテンプレート経由を表示し、AIが利用できる場合は既存のAI経由を初期表示する案とする。見出しはAI限定の説明から、ページ作成全般の説明へ変更する。
- テンプレート作成は既存のAI・白紙用フォームと分ける。AI入力を保持したまま切り替えられることを説明し、テンプレート送信にAI指示を含めない。
- 管理画面の名前・説明・「日本語」バッジは英語リテラルを元にPHPの翻訳関数で定義する。日本語のページ本文は全管理画面ロケールで提供し、本文の言語を明示する案とする。
- 第1弾ではプレースホルダーをページごとに登録し、別ページ間の画像再利用・共有キャッシュは行わない。同一ページ内の同じ画像IDだけを1つの添付へ解決する。

## 5. 作成物と配置案

下記は新規ファイルの配置案。既存のPHP描画用`templates/`と区別する。

```text
assets/templates/
  free/general-service-lp/
    manifest.json
    index.html
    style.css
    thumbnail.webp
    images/landscape.png
    LICENSE.txt

includes/
  class-kayzart-template-library.php
  class-kayzart-template-page-creator.php

scripts/templates/
  README.md
  （必要な撮影用写真・ライセンス記録。自動生成スクリプトは必須にしない）

docs/
  free-template-v1-master-plan.md
```

- `assets/templates/`の定義・画像・ライセンス記録は配布ZIPに含める。利用者入力によるファイル追加は第1弾では行わない。
- 写真入りの見本は開発時の撮影用にだけ使用する。元写真をページ作成用データへ入れない。
- サムネイル自体は配布物であるため、その中に写る写真にも配布に適した権利・GPL互換性を確認する。「元写真を同梱しない」だけで確認を省かない。
- 本文は`index.html`、CSSは`style.css`を正本とし、`manifest.json`にはメタデータとファイル参照だけを置く。完成LPのHTML・CSSをJSON文字列へ手でエスケープして編集しない。
- 一覧の許可ID・フォルダ・翻訳可能な名前と説明はPHPの小さなレジストリで定義する。1点だけの第1弾で別の`catalog.json`を手管理しない。
- 写真入りサムネイルの撮影手順を記録し、定義の検証はテストで行う。専用のアセット生成ツールは、反復作業に必要となったときに追加する。
- `docs/`と`scripts/`は現行`.distignore`で配布対象外。実行時にこれらを参照しない。
- `assets/dist/`はビルド生成物として扱い、手編集・Git追加しない。

## 6. 汎用LPと画像の制作仕様

### 6.1 ページ構成案

| 部分 | 制作内容 |
|---|---|
| ヘッダー | 文字でも成立する事業名、ページ内ナビ、問い合わせ先への導線 |
| メインビジュアル | 見出し、説明文、行動ボタン、差し替え画像 |
| 特徴 | 選ばれる理由を3点程度 |
| サービス内容 | 業種固有の機能に依存しない紹介カード |
| 料金 | 料金・提供内容の差し替え例。サンプル価格と分かる案内 |
| 利用の流れ | 相談から利用開始まで |
| FAQ | サービスに合わせて変更できる質問・回答 |
| 問い合わせ・フッター | 設定箇所が明確な連絡先、事業者情報 |

完成ページの縦構成を用意する。実績数値、口コミ、受賞歴、所在地などの事実を創作して実在情報のように置かない。ダミー情報は架空のサンプルだと分かるものにする。

フォーム送信バックエンドは実装しない。問い合わせボタンはページ内のサンプル問い合わせ欄へ移動し、全アンカー先を用意する。操作説明はエディタ側の案内に置き、公開本文に「ここで設定してください」といった管理画面向けの文章を残さない。サンプル欄はサンプルであることを明示し、架空の実在メールアドレスや電話番号への発信リンクを置かない。

テンプレート内のJavaScript、イベント属性、外部スクリプト、カスタムhead、インラインSVG、`form`・`input`などのフォーム部品を第1弾では使わない。アイコンは文字や許可された`img`で表し、CSSはクラスを基本とする。FAQは見出しと回答を常時表示し、`details`・`summary`への依存も第1弾では持たせない。

プレビューと作成処理の両方で、画像トークンを有効なローカルURLへ解決してから`wp_kses_post()`を通す。最終的に保存するHTMLに対して候補クラスを抽出・コンパイルし、権限の有無で表示が変わる要素を制作段階で除く。画像トークンを未解決のままksesへ渡してURLとして削らせない。

### 6.2 画像・フォント

- サムネイルは、実テンプレートのプレースホルダー画像だけを撮影用写真へ置換して撮る。HTML・CSSのレイアウトを別物に作り替えない。
- 一覧から選ぶ前と詳細の両方で、写真が使用例であることを短く伝える。文言例:「写真は使用例です。作成後にご自身の画像を設定してください。」翻訳対象にする。
- 詳細プレビューはプレースホルダー版を表示し、作成後の状態を事前確認できるようにする。
- 写真とプレースホルダーの表示比率・枠寸法をそろえる。1枚を複数箇所で使う場合も、既存の画像差し替え操作で各箇所を独立して変更できることを確認する。
- ページ内画像は通常の`img`を基本とし、CSS背景画像や複雑な`picture`による差し替え難度を増やさない。
- プレースホルダーの代替テキストは`alt=""`を基本とする。差し替え方法をaltへ書かず、実画像を設定したときに説明に合うaltを入力するようエディタ側で案内する。
- 表示はシステムフォントを基本とする。閲覧時にGoogle Fontsなどを要求しない。
- 写真・プレースホルダー・アイコンのライセンス、出典、加工内容を記録する。自作・権利確認済みの素材を選ぶ。
- 画像サイズ・配布容量はP1で計測する。現時点で根拠のない容量値をリリース要件として固定しない。

## 7. 一覧・定義データの形式案

第2弾のZIPでも同じページ定義を運べるようにするが、ZIPの仕様・購入認証・権利管理はここでは実装しない。

| データ | 最低限持つもの |
|---|---|
| 一覧用PHPレジストリ | 許可済みテンプレートID・ローカルフォルダ・英語リテラルの名前と説明。`__()`などで管理画面へ翻訳して表示 |
| `manifest.json` | `schemaVersion`、`id`、`version`、`kind: page`、`locale`、`cssMode`、`layoutMode`、本文・CSS・サムネイルの相対パス、画像宣言 |
| `index.html`・`style.css` | 人が直接編集するページ本文とTailwindソース。表示名・説明の翻訳辞書としては使わない |
| 画像宣言 | 定義内の画像ID、相対ファイルパス、形式・寸法。ページ内のaltはHTMLで指定 |

例（メタデータの形式案。本文・スタイル・画像は記載の別ファイルに置く）:

```json
{
  "schemaVersion": 1,
  "id": "general-service-lp",
  "version": "1.0.0",
  "kind": "page",
  "locale": "ja",
  "cssMode": "tailwind",
  "layoutMode": "standalone",
  "files": {
    "html": "index.html",
    "css": "style.css",
    "thumbnail": "thumbnail.webp"
  },
  "assets": [
    {
      "id": "main-visual",
      "path": "images/landscape.png",
      "mimeType": "image/png",
      "width": 1600,
      "height": 900
    }
  ]
}
```

- 本文では`<img src="{{asset:main-visual}}" alt="" ...>`のように画像IDを参照する。`{{asset:...}}`は宣言済みIDだけを解決し、プレビューでは同梱画像URL、作成時には登録したメディアURLへ置換する。
- 未解決参照、ID重複、未知のschema、未対応モード、外部ファイルパスはエラーにする。
- 相対パスはPHPレジストリが選んだテンプレートフォルダ配下に限定する。ブラウザから任意のパス・URL・HTML・CSSを受け取って作成しない。
- 版は「データ形式の版」と「各テンプレートの版」を分ける。同じIDの改版は次の新規作成にだけ反映する。
- 日本語本文1点は全管理画面ロケールで表示し、「Japanese」を翻訳する言語バッジと、本文が日本語である説明を必ず付ける計画とする。日本語ロケール以外で非表示にはせず、本文を自動翻訳もしない。これはレビュー反映の設計案であり、ユーザーが本文の言語を別途指定した場合は再調整する。

## 8. Add newとプレビューの動作

1. Add new上部の3つの開始方法から選ぶ。選択UIはAI接続案内より上に置き、AI未設定ならテンプレートを初期表示する。AI接続案内はAI経由のパネル内で表示する。
2. テンプレートカードに写真入りのサムネイル・翻訳可能な名前と用途・本文の言語バッジ・写真の説明を表示する。
3. 詳細を開くとプレースホルダー版を表示する。PC・スマホ幅を切り替えられる。
4. タイトルを入力して「このテンプレートで作成」を押す。空欄なら翻訳可能な仮タイトルを使用する。
5. 成功時は`kayzart_entry=template`付きで下書きのKayzartエディタを開く。初回だけコードを畳み、要素編集パネルを開いて、画像・文章・連絡先を変更する案内を表示する。

テンプレート専用フォームをAI・白紙用フォームから分け、`start_mode=template`・テンプレートID・タイトル・リクエストID・nonceだけを送る。AI指示はその専用フォームに含めない。AI入力は元のフォームに保持し、「AIの入力はAIで作成に戻ると続けられます」と説明する。白紙で作る際に指示の消去を求める既存ルールは維持する。

`new-page.js`の「AI以外をblankにする」送信処理をそのままテンプレートフォームへ適用しない。PHPの`read_requested_start_mode()`、エディタへ渡す`kayzart_entry`の許可値、`InitialEntryMode`、アプリ設定型、`resolveInitialEditorLayout()`も`template`に対応させる。未知の値をAI経由へ推測して送らないよう、明示的な不正値を拒否し、旧リンクのパラメータ省略時の互換処理とは分ける。

テンプレート経由はサーバー側で`page`・Tailwind・Standaloneを固定し、送信された`post_type`や`mode`で上書きしない。UIでもモードを説明表示にする。AI・白紙経由の投稿タイプ・CSSモード選択は維持する。

`page`がKayzartで無効、作成権限なし、`upload_files`なしの場合は、入口の時点で理由と利用できない操作を示す。権限不足を理由にAdd newのAI・白紙経由まで消さない。送信時とプレビュー取得時にも権限を再確認する。

エディタのテンプレート初期表示は作成直後の入口だけに適用する。既存のURLパラメータ消費処理に接続し、通常の再編集で毎回レイアウトを強制しない。個人の保存済みレイアウトを初期案内だけで上書きしない。

### 8.1 プレビューの生成・キャッシュ・隔離

- 詳細を開いたときだけ、nonceと権限を確認する読み取り専用のGET admin actionへ同一サイト内で要求し、プレビュー用HTMLを生成する。Add new表示のたびにコンパイルしない。
- 投稿IDは不要とし、既存の投稿用`/compile-tailwind`をダミー投稿付きで呼ばない。実際の保存と同じサニタイズ・候補抽出・コンパイル処理を使う。
- プレビュー結果は再生成可能なtransientにキャッシュする。キーにはテンプレートID・版、プラグイン版、定義ファイルの内容ハッシュを含め、プレビューURLが変わるサイト設定も考慮する。権限確認はキャッシュ取得前にも行う。
- 応答を`iframe.srcdoc`へ設定し、`sandbox`には`allow-scripts`・`allow-same-origin`・フォーム送信・上位遷移の許可を付けない。
- 生成文書にはCSPを設け、画像は同梱画像のURLに必要な配信元・パスだけを許可する。外部画像・フォント・スクリプトを許可せず、コンパイル済みのインラインCSSは表示できるようにする。`srcdoc`の基準URLとsandbox下のオリジンを考慮して実ブラウザで確認する。
- PC・スマホ切替、閉じる操作、フォーカス復帰、キーボード操作を確認する。キャッシュがなくても投稿や添付ファイルは作成しない。

## 9. ページ作成と保存の実装方針

### 9.1 作成処理の流れ

1. nonce、ログイン、`page`の作成権限、Kayzartでの固定ページ有効状態、画像登録に必要な`upload_files`を検証する。
2. テンプレートID・リクエストID・タイトルを受け取り、PHPレジストリから定義を解決する。リクエストからのHTML・CSS・投稿タイプ・モード指定では定義を上書きしない。
3. 定義・同梱画像を検証する。画像トークンを同梱画像のURLへ解決して`wp_kses_post()`を適用し、候補抽出・コンパイルを事前検証する。
4. 同一要求の予約を取得し、リビジョン自動作成フックを一時抑制した範囲で固定ページの下書きを作る。その要求のIDを投稿メタへ保存する。
5. 同梱PNGを一時ファイルへコピーし、当該ページの添付として登録する。同一ページ内の同じ画像IDだけを再利用し、外部HTTPで取得しない。
6. 元の本文のトークンをメディアURLへ解決して再度ksesを通し、最終HTMLの候補クラスとCSSを確定する。事前結果を再利用する場合も最終HTMLの候補集合と一致することを確認する。
7. 第9.2節の順序で本文・CSS・各モード・設定を保存し、DBから再取得して検証する。要求を完了状態にして、`kayzart_entry=template`付きの既存エディタURLへ遷移する。

作成処理は既存のnonce付きadmin actionを拡張する案を基本とする。新しい公開REST APIや、外部配信サーバーは必須にしない。

### 9.2 保存順序とリビジョン

テンプレート作成は既存の白紙作成処理へCSSを足すだけにはしない。テンプレート経由では`apply_setup_mode()`と`Css_Mode::initialize_post_mode()`を呼ばず、次の状態を明示的に保存する。

1. 現在のフック登録状態を記録し、`wp_after_insert_post`の`wp_save_post_revision_on_insert`と`post_updated`の`wp_save_post_revision`を、登録されている場合にだけ一時的に外す。途中失敗を含め`finally`で元の状態へ戻す。
2. `post_type=page`、`post_status=draft`、作成者・タイトルと、最終的に確定した本文を保存する。本文の変更で中身の欠けたリビジョンを先行作成しない。
3. Kayzartを有効化し、`_kayzart_css`と`_kayzart_tailwind_css`にテンプレートのTailwindソースを保存する。
4. **`_kayzart_normal_css`は未作成にし、フロントへ`normal: null`を渡す。空文字を保存しない。** 現行の`resolveCssModeChange()`は`null`の場合だけNormal用の生成CSSを初回変換するためである。Tailwind→Normal→Tailwindの表示保持をテストする。
5. 生成CSS・候補クラス、`_kayzart_tailwind=1`、`_kayzart_tailwind_locked=1`、`_kayzart_template_mode=standalone`を保存し、`_kayzart_setup_required`を削除する。初回AIリクエストは保存しない。
6. テンプレートの由来として`_kayzart_template_id`・`_kayzart_template_version`を保存する。現在参照中のメディア一覧をページメタとして別管理せず、本文の画像URLを正本にする。
7. 期待するスナップショットと`Snapshot::for_post()`のハッシュを比較する。PHP 7.4・WP 5.9でも、保存状態の検証は履歴対応の有無と分けて行う。
8. `Snapshot::is_supported()`かつ`Snapshot::revisions_enabled()`の場合だけ完全な初回リビジョンを作り、その内容とハッシュを確認する。履歴無効・WP 6.4未満ではリビジョンなしで正しく保存できることを確認する。

`_kayzart_css`だけを書いて終わりにしない。保存形式は現在の`Rest_Save`と`Snapshot`にそろえ、既存経路へ影響する共通化は最小限にする。初期のモード指定を固定することと、作成後の既存モード切替機能を禁止することは分ける。

### 9.3 画像登録・寿命・権限

- `wp_tempnam()`で得た一時パスへ同梱画像をコピーし、`media_handle_sideload()`でローカルファイルとして登録する。一時ファイルは成功・失敗の両方で後始末し、コピー元をsideloadへ渡して移動・削除させない。
- 第1弾はページ単位の登録にする。1つの画像IDを同一ページ内で何度参照しても登録は1回。別ページで使う画像は別の添付とし、共有画像の削除競合・再利用キャッシュ・参照カウントを実装しない。
- 添付側にテンプレートID・画像ID・内容ハッシュと所有リクエストを記録し、当該要求で作ったファイルの識別に使う。登録後は添付IDだけで成功扱いにせず、URL・実ファイル・必要な寸法情報が取得できることを確認する。
- WordPress標準のMIME・メタデータ処理を使うが、sideloadだけで権限・容量・画像処理成功をすべて保証できると仮定しない。呼び出し前の権限・許可形式・必要な容量の検証と、書き込み不能・GD/Imagickなどが利用できない場合の結果をテストする。派生サイズが作れない場合と、元画像自体を登録・表示できない場合を区別する。
- サムネイルと詳細プレビューは同梱パスを参照してよい。作成済みページはuploads内のメディアURLを参照する。利用者がメディア自体を削除した場合の自動修復は行わない。
- `upload_files`を持たない利用者へ権限を自動付与しない。入口で制約を案内し、サーバーでも検証する。AI・白紙経由の既存権限は維持する。
- サムネイル撮影用の元写真は、利用者のメディアへ登録しない。

### 9.4 重複送信と失敗

- 既存と同様、送信中はボタンを無効化する。フォームのリクエストIDはユーザーとひも付け、完了した要求は`_kayzart_template_request_id`と完了マーカーを持つ下書きから解決する。再送は作成者・権限・テンプレートの一致を確認して、その下書きへ戻す。
- 処理中の同一要求だけ、ユーザーIDとリクエストIDをキーに`add_option()`で原子的に予約する。非autoloadの予約とし、取得後にも完了済み下書きを再確認する。予約を取れない並行要求は作成せず、処理中と案内する。
- 通常の完了・捕捉できる失敗は`finally`で予約を解除する。恒久的な失敗台帳・管理画面・専用テーブル・バックグラウンド監視は作らない。異常終了で残る予約の判別・安全な回収だけP3で最小設計を確定し、稼働中の要求を無条件に横取りしない。
- 応答だけが失われた場合は投稿メタから完了済みの下書きへ復帰する。不完全な投稿を完了済みとして戻さず、同じ要求による未完了データの回収・再試行を扱う。
- 定義不正・コンパイル失敗・画像登録失敗を成功扱いにしない。入力とエラーを保ち、再試行できる表示にする。
- 捕捉できる途中失敗は、この要求が新規作成した添付を`wp_delete_attachment(..., true)`、未完成の下書きを`wp_delete_post(..., true)`で回収する。複製などで参照された既存画像・既存投稿を巻き込まない。
- 一時ファイル・元画像・派生画像の回収結果も確認する。回収に失敗した場合は成功遷移せず、既存のエラー通知・ログへ必要な情報を残す。異常終了を含む全障害に対する厳密な一括トランザクションは第1弾の保証に含めない。

### 9.5 既存の複製機能

`copy_kayzart_post_data()`は`_kayzart_`メタを既定でコピーする。由来を示すテンプレートID・版は複製先へ残すが、作成リクエストID・完了マーカーなどの要求固有メタは`DUPLICATE_META_DENYLIST`へ追加し、再送先が複製投稿になることを防ぐ。画像は既存の複製機能と同じく本文内のURLを引き継ぎ、複製時に再登録しない。

## 10. セキュリティ・互換性・掲載ルール

- PHP 7.4以上、現行のWordPress最低要件5.9を維持する。PHP 8限定構文を使わない。
- 固定ページ作成・メディア登録の権限とnonceをサーバーで確認する。管理画面が見えるだけで作成を許可しない。
- 同梱HTMLもkses後の許可要素で作成し、保存前に再検証する。インラインSVG・フォーム部品・イベント属性などで`unfiltered_html`のない利用者に保存前後の差を生じさせず、任意コード挿入経路で権限を迂回させない。
- パスはカタログ内の許可済みファイルから決める。パストラバーサル・任意URL指定・未知のテンプレートIDを拒否する。
- HTML・CSS・画像URL・翻訳文字列は、それぞれの出力先で適切に扱う。テンプレートのスタイルやタグを管理画面へ直接流し込まない。
- テンプレート機能による外部HTTP、外部画像、外部フォント、分析タグ、バックグラウンド同期を追加しない。既存のWordPress更新通信などまで停止する意味ではない。
- 同梱JSON・写真入りサムネイル・プレースホルダーを含め、配布ファイルのGPL互換性・出典を確認する。素材を後から揃える場合は、権利確認をP1の完了条件に含める。
- 第1弾に購入解除を前提とするテンプレート本体・機能を含めない。今回の設計を理由に将来の有料版の掲載適合まで保証しない。

参照した公式資料（確認日: 2026-10-26）:

- [WordPress.org Detailed Plugin Guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/) — 同梱物のライセンス、第5条の機能制限、第7〜8条の外部通信・コード配信。
- [WordPressの画像MIME一覧](https://developer.wordpress.org/reference/functions/wp_get_mime_types/) — PNG/WebPなど。実際の許可形式・画像処理可否はサイト環境でも確認する。

### 12.2 自動テストの重点

- PHP: レジストリ／manifest／HTML・CSSの検証、許可パス、権限、kses後の表示、正しい保存順序・モード状態、ページ単位の画像登録、再送・競合、失敗回収・複製メタを中心にテストする。
- フロント: 専用フォーム、開始方法の切替、AI指示の誤送信防止、言語と写真の説明、入力保持、初期レイアウト、送信中制御を確認する。
- E2E: AI未設定での一覧→詳細→下書き→画像差し替え→保存→公開表示の1経路を優先する。Playwrightではブラウザ側の外部通信を遮断し、同一サイトの管理画面・メディアは許可する。
- PHP側のHTTPは別途PHPUnitの`pre_http_request`で捕捉し、テンプレート経路が外部HTTPを発生させないことを確認する。Playwrightだけでサーバーの通信を遮断できるとは扱わない。
- PHPUnitは既存CIのWP 5.9/PHP 7.4を含むマトリクスへ追加する。リビジョン境界のWP 6.3と6.4でも作成・保存・履歴のテストを実施するため、この2組のケースをCIへ追加する計画とする。
- テンプレート経路の主要E2Eは最低環境WP 5.9/PHP 7.4と、リリース時点の最新対応WordPress環境で実施する。境界版すべてへのE2E拡大は要件にせず、6.3／6.4はPHPUnitで検証する。
- GD/Imagickなし、uploads書き込み不可、nonce失効、画像登録失敗、応答喪失・並行送信を、独立した環境またはフェイクで検証する。
- E2Eの新規データは必ず固定ページ。共通ヘルパーにテンプレートUIで作成された投稿IDの捕捉・回収を組み込み、作成・変換・削除を共通化する。
- 一時ページは`finally`で削除し、削除レスポンス成功を検証する。再ログイン・画面遷移後は現在のREST nonceを取り直す。`wp-json/wp/v2/kayzart`を呼ばない。
- テスト用添付ファイルも識別・回収し、既存の利用者データや共有添付を削除しない。

### 12.3 検証コマンドと配布手順

実装した範囲に合わせて既存の`npm run test:unit`、`composer test`、`composer phpcs`、`npm run e2e -- <対象spec>`を使う。PHP互換性チェック・Plugin Check・実配布ZIP確認もリリース前に実施する。前提環境不足のチェックを「合格」と記録しない。

配布は既存の`npm run plugin-zip`（ビルド→本番依存→ZIP作成→開発依存の復元）を基本とし、生成物を手編集・Git追加しない。Viteの`emptyOutDir: true`によりビルド時にも出力は空になるが、ワークスペースAGENTS.mdの「ビルド前にクリーンする」指示は維持する。削除する場合は絶対パスがこのリポジトリの`assets/dist/`であることを先に確認し、PowerShellで安全に実施する。`scripts/plugin-zip.mjs`は作業ツリーを`.distignore`で選別するため、同梱資産と撮影用ファイルの両方について実際のZIP内容を検査する。

readme・変更履歴・必要な管理画面翻訳を更新する。素材ライセンス記録と写真説明の翻訳も配布物で確認する。mainへの取り込みはPR経由とし、実装完了と本番リリースを別の状態で記録する。

### 16.1 修正案をそのまま採らなかった根拠

- `resolveCssModeChange()`はNormalバッファが`null`のときだけコンパイルする。空文字は有効な既存バッファとして扱うため、空文字の保存では初回切替時にスタイルがなくなる。Adminの初期データ生成と`Snapshot::for_post()`は、メタ未作成を`null`へ変換することも確認した。
- 投稿と画像を別々に回収することを分かりやすくするため、添付には明示的に`wp_delete_attachment()`を使う。なおWordPressの`wp_delete_post()`も添付の場合は内部で同関数へ委譲するため、レビューの削除APIが動かないという判断ではない。
- `media_handle_sideload()`は登録後に画像メタデータ生成を呼ぶが、添付IDの返却だけで必要な画像処理の成功まで確認できるわけではない。利用可能な元画像の登録と派生サイズ生成の可否を分けて検証する。
- Viteが出力を空にすることと、明示された「ビルド前にクリーンする」作業指示は別である。本計画では後者を削除しない。
